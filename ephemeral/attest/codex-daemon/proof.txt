Proof for issue #143 (commit 2 of 2, fixing round-01 review findings): the
codex adapter attaches to the machine's one shared `codex app-server`
daemon, reuses one WebSocket connection across every session and turn, and
recovers from a dead connection by resuming every thread it knows about
before handing the new connection to any caller.

Model used: gpt-5.6-luna (Codex), the cheapest Codex model, for every turn
in both the attest program and the live test below.

## Finding 1 fix: a redialed connection now re-subscribes existing threads

`adapter.conn` (codex/codex.go) now calls a new `resumeThreads` before
handing out a freshly dialed connection: for every session the adapter
knows about, it sends `thread/resume` with the same params the old
per-process adapter used (`threadId`, `cwd`, `approvalPolicy: "never"`,
`sandbox: "danger-full-access"`), checks the returned thread id matches,
and registers the thread for routing on the new connection. If any resume
fails, `conn(ctx)` returns that error rather than handing back a
half-subscribed connection. `turn/start` alone was never enough: only
`thread/start`, `thread/fork`, and `thread/resume` add the calling
connection to a thread's subscriber set in the daemon.

## Commit 2: HarnessAdapter.Close, called for real when a scope ends

Model used: gpt-5.6-luna (Codex), for the turn in the live test below.

`HarnessAdapter` now has a required `Close(ctx, sessionID) error` method.
`scope.end` (gimble/scope.go) calls it for every adopted session that has a
native id, on a `context.WithTimeout(context.Background(), 10*time.Second)`
independent of the run's own ctx, and records `SessionClosed{Error}`
either way. A session with no native id (never ran a turn) gets no Close
call. Close failures never enter the scope's own error; they are pushed
onto the run under a mutex and Run joins the aggregate as a new `*CloseError`
into its returned error, alongside `RunEnded.Error`, once the root scope has
ended.

The Codex adapter's `Close` (codex/codex.go) removes the session from
`a.sessions`, deregisters the thread from the shared connection's routing
table (`connection.unregisterThread`, the counterpart to `registerThread`),
and — only if the shared connection still exists and its reader has not
already failed — sends `thread/unsubscribe {"threadId": id}` on it. A
`status` of `unsubscribed`, `notSubscribed`, or `notLoaded` is treated as
success. It never sends `thread/archive` or `thread/delete`, and it never
touches the connection or the daemon process itself: the thread stays
loaded in the daemon, which owns that retention decision. An unknown id
(never registered, or already closed) returns nil without a network call.

Reading the evidence:

- Both `sessions` and `threads` maps were empty after `Run` returned: Close
  ran for the plain session and for the fork, and nothing was left
  registered client-side for either.
- `thread/unsubscribe` returned `unsubscribed` for both threads: the daemon

  (never a fresh dial, since Close does not touch the connection), still
  listed both unsubscribed threads alongside every other thread this

  retention policy, not something this adapter controls or should assert
  about.
- The managed daemon's pid was 1516 before and after, matching
  `pgrep -fl 'app-server --listen unix'` run independently right before
  this attestation: Close never stopped or restarted the shared daemon.

### What was left out and why

- Immediately after this passing run, further live re-runs against the same
  long-lived daemon (in this same session, verifying idempotence and
  re-checking the commit-1 redial test) started failing with the daemon's
  own `Fatal error: ... Too many open files (os error 24)` when opening a
  new thread-writer lock file — an EMFILE from the daemon process itself,
  hit while creating a brand new thread, not from anything `Close`
  unsubscribed or any connection this adapter held open. The daemon's pid
  stayed 1516 throughout: it did not restart, crash, or get touched by this
  adapter; it is simply low on file descriptors after the day's cumulative
  attestation traffic (this and earlier proof rounds) against one
  long-running shared process. Since the daemon must never be stopped or
  restarted by this adapter, no attempt was made to work around or clear
  that state; the passing run captured above is the proof, taken before
  that exhaustion appeared. Idempotence (`Close` on an unknown id, twice)
  is instead proven without any daemon traffic at all, in
  `codex/codex_test.go`'s `TestCloseIsIdempotentForAnUnknownSession`, and
  correspondingly for Claude in `claude/claude_test.go`.
- Every other acceptance item (the scope-error/CloseError contract, the
  cancelled-run close-with-fresh-context guarantee, the no-native-id case,
  and `Complete.RecordingError`'s independence from close failures) is
  proven with a fake adapter in the root package's `issue143_test.go`,
  which needs no live daemon.
