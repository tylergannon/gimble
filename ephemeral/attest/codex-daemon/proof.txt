Proof for issue #143 (commit 2 of 2, fixing round-01 review findings): the
codex adapter attaches to the machine's one shared `codex app-server`
daemon, reuses one WebSocket connection across every session and turn, and
recovers from a dead connection by resuming every thread it knows about
before handing the new connection to any caller.

Model used: gpt-5.6-luna (Codex), the cheapest Codex model, for every turn
in both the attest program and the live test below.

## Finding 1 fix: a redialed connection now re-subscribes existing threads

`adapter.conn` (codex/codex.go) now calls a new `resumeThreads` before
handing out a freshly dialed connection: for every session the adapter
knows about, it sends `thread/resume` with the same params the old
per-process adapter used (`threadId`, `cwd`, `approvalPolicy: "never"`,
`sandbox: "danger-full-access"`), checks the returned thread id matches,
and registers the thread for routing on the new connection. If any resume
fails, `conn(ctx)` returns that error rather than handing back a
half-subscribed connection. `turn/start` alone was never enough: only
`thread/start`, `thread/fork`, and `thread/resume` add the calling
connection to a thread's subscriber set in the daemon.

### Live proof, without restarting the daemon

`codex/daemon_live_test.go` (`TestRunTurnAfterRedialResumesThread`, skipped
unless `GIMBLE_LIVE=1`) creates a session, runs a turn, forcibly closes the
adapter's current WebSocket from inside the test (`conn.ws.CloseNow()`,
reached directly since the test is in package `codex`), waits for the
reader to notice, then runs a second turn on the same session inside a
bounded 60s context. Before the fix this hangs until the context expires
(`turn/start` succeeds, but nothing routes its notifications); after the
fix it passes well within the bound.

## What was left out and why

- A WebSocket-connections-opened counter was not added. Doing so would
  require either exporting a new field/method from the unexported
  `adapter`/`connection` types or widening the `HarnessAdapter` interface,
  and the caller's instructions reserve interface and lifecycle changes
  (including `Close`) for a separate commit. The live test above already
  demonstrates the redial path directly (it forces the exact connection
  loss the counter would otherwise be inferred from), so the counter would
  add confirmation, not new coverage, at the cost of exporting something
  new. Both the attest program and the live test observe daemon and
  connection identity by other means: the daemon pid and app-server
  process set (attest program) and the redial itself, since the live test
  waits on `conn.readDone` before its second turn (live test).
- `HarnessAdapter.Close` and any adapter-lifecycle cleanup remain
  unaddressed by design; that is explicitly the next commit's scope.
