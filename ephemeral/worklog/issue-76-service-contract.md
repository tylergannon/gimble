# Issue 76: service contract interview

decision: Tyler — A workflow may name at most one system file. Initially only Procfile format is supported, including alternate filenames such as Procfile.dev. Compose support is deferred.
decision: Tyler — The service port must be available in all shell environments used by the workflow. Status-only discovery is insufficient. Tyler permits recording the port in runtime checkpoints too.
decision: Agent recommendation — Use TRACTOR_SERVICE_PORT for the workflow-facing variable so it is distinguishable from Overmind's process-local PORT. Tyler offered both names; this spelling is the agent's recommendation.
correction: Tyler rejected identifying the workflow-facing service by the first Procfile entry. The earlier agent recommendation is superseded.
decision: Tyler — Permit zero or one named service in the workflow for now, replacing issue 76's arbitrary number of named services. An array is acceptable with this cardinality limit; broad multi-service support must not delay delivery.
decision: Agent interpretation — The named service selects the corresponding Procfile process. TRACTOR_SERVICE_PORT exposes the PORT assigned to that process, without requiring it to be first. Other processes may exist in the system file; only one is addressable as a workflow service. Overmind supplies a distinct process-local PORT to each process, so PORT alone cannot select a process from a multi-process Procfile.
correction: Tyler stopped the parallel issue 76 implementation in worktree 5073 because its service-node and graph-edge migration followed the older broad issue design and would create substantial rework. The narrow contract supersedes that design.
decision: Agent implementation — Put `system_file` and `services` at workflow level. Either both are absent, or `system_file` names a Procfile and `services` contains exactly one selected process. There are no service nodes or requirement edges in this checkpoint. Compose remains deferred.
