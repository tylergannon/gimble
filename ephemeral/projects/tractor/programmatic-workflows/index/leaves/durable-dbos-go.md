# DBOS Transact Go: PostgreSQL checkpointed steps

**Purpose.** DBOS Transact is a real Go implementation, not a TypeScript/Python-only lead. It allows ordinary Go workflow functions and uses a Postgres-backed step ledger. It gives the clearest inspected source answer to the crash-after-effect-before-record problem.

**Findings.**

- The registered workflow type is generic and typed: `func(ctx Context, input P) (R, error)` (`durable/dbos-go/workflow.go.txt:664-779`; [pinned source](https://github.com/dbos-inc/dbos-transact-golang/blob/ab56911fdd78552e1e7fe648cff7c831a1e760c8/dbos/workflow.go#L664-L779)). `RunWorkflow` returns a typed handle and says input/results are persisted (`durable/dbos-go/workflow.go.txt:968-1037`; [pinned source](https://github.com/dbos-inc/dbos-transact-golang/blob/ab56911fdd78552e1e7fe648cff7c831a1e760c8/dbos/workflow.go#L968-L1037)). This is directly relevant to typed per-call agent results.
- `RunAsStep` explicitly offers **at-least-once** execution; recovery returns an existing checkpoint rather than re-running the function (`durable/dbos-go/workflow.go.txt:2527-2531`; [pinned source](https://github.com/dbos-inc/dbos-transact-golang/blob/ab56911fdd78552e1e7fe648cff7c831a1e760c8/dbos/workflow.go#L2527-L2531)). It accepts an ordinary Go callback, so its control flow is author-friendly but every effect must be placed at a meaningful boundary.
- The implementation checks for a completed operation, runs the callback when none exists, and only afterwards serializes/records its output (`durable/dbos-go/workflow.go.txt:2623-2689`; [pinned source](https://github.com/dbos-inc/dbos-transact-golang/blob/ab56911fdd78552e1e7fe648cff7c831a1e760c8/dbos/workflow.go#L2623-L2689)). This is direct source proof of the crash window: an HTTP call can succeed, then a crash before `RecordOperationResult`, causing re-execution. It is not a theoretical warning.
- The source has a stronger path for database effects: `runAsTxn` says the step body and checkpoint share one transaction (`durable/dbos-go/workflow.go.txt:2692-2694`; [pinned source](https://github.com/dbos-inc/dbos-transact-golang/blob/ab56911fdd78552e1e7fe648cff7c831a1e760c8/dbos/workflow.go#L2692-L2694)). The official Go transaction guide specifies that this makes the application write and durability record atomic when targeting the relevant database ([guide](https://docs.dbos.dev/golang/tutorials/transaction-tutorial)). That solves a DB effect, not a GitHub/CI/deploy effect.
- Native `go`/`select` scheduling is declared nondeterministic by DBOS's Go workflow guide; DBOS provides durable `Go` and `Select`, both present in source (`durable/dbos-go/workflow.go.txt:2867-2963`; [pinned source](https://github.com/dbos-inc/dbos-transact-golang/blob/ab56911fdd78552e1e7fe648cff7c831a1e760c8/dbos/workflow.go#L2867-L2963); [guide](https://docs.dbos.dev/golang/tutorials/workflow-tutorial)). Thus this is code-first, but not unconstrained standard concurrency.

**Recovery and relevance to coding workflows.** DBOS proves that a named checkpoint ledger can resume work, but it also proves why full replay is not automatically valuable here. For a normal agent attempt that only edits a repository, restart can read the diff, run named validators anew, and replan toward the current goal. Add a persisted named stage only when it records an authority-bearing human answer, an effect that cannot be deduplicated/read back from its provider, or a validation result whose freshness is itself contractual. A PR/deploy made by an externally idempotent API can use its external ID and be rediscovered; a human answer needs a durable decision record; a green test result should generally be recomputed after any repository change.

**Visualization.** The source records workflow statuses/step IDs after the fact, and `RunAsStep` names steps (`durable/dbos-go/workflow.go.txt:2587-2589`). It does not statically enumerate future concrete instances of a general function. A source-derived structural outline can still show syntactic calls and both branches, marking opaque/dynamic calls and runtime-sized fan-out; a separate declared graph is a product choice only when it carries information source inspection cannot. The current graph likewise cannot know the actual agent outcome, so neither representation should claim a run-specific topology before execution.

**Themes.** ordinary typed Go; at-least-once steps; atomic database transactions; recovery ledger; deliberate static contract.

**Gotchas.** Do not state “exactly once” for `RunAsStep`; the source says at-least-once. A transaction's stronger guarantee only covers a transactionally shared database. A workflow cancellation mid-step intentionally leaves no checkpoint and re-executes on resume (`durable/dbos-go/workflow.go.txt:2571-2575`).
