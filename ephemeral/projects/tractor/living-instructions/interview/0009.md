# Execution workflow build-directory parameter

Chapter 3 says `medium` and `large` each take the build directory as their
single parameter, while decision 25 keeps `$goal` as the only graph
substitution. Chapter 2 already emits these handoffs:

```text
tractor workflow run medium --project <build>
tractor workflow run large --project <build>
```

How should the execution workflows receive and resolve that directory?

1. **Keep `--project <safe-name>` (recommended).** Treat `--project` as the
   one workflow-specific parameter and derive
   `<workdir>/ephemeral/projects/<project>` before materializing the embedded
   graph. `--workdir` and `--logs` remain common runner controls, not workflow
   parameters. The materializer writes the resolved checklist/doc paths into
   node fields and prompts, so no new graph substitution is needed.
2. **Add `--build-dir <relative-path>`.** Accept an explicit directory below
   the workdir. This is more flexible, but contradicts the handoff chapter 2
   now emits and broadens path validation.
3. **Put the directory in `$goal`.** Preserve the CLI but encode the directory
   as goal text for nodes to interpret. This avoids typed materialization but
   makes loop checklist paths impossible to bind mechanically.

I recommend option 1 because it preserves the ratified handoff, keeps one
workflow parameter, and requires no graph-language feature.
