# HALF A — The Attractor lineage

## Lineage, verified (with a correction to the task premise)

The chain is: **StrongDM's Attractor spec → tylergannon/attractor (archived) → Tractor.** The Steve Yegge attribution in the prompt is folklore, and could not be confirmed against any primary source:

- `tylergannon/attractor` at rev `0aca8b7` carries a pristine upstream copy with the header: "This is a pristine copy of the upstream StrongDM Attractor specification: https://github.com/strongdm/attractor/blob/main/attractor-spec.md" (`docs/attractor-spec.md` lines 1–11). Its `docs/spec.failed.md` Appendix E states "This specification is a direct descendant of StrongDM's upstream `attractor-spec.md`" with a section-by-section provenance table (Borrowed/Adapted/Replacement/Local).
- The original is **StrongDM's**, released ~Feb 7 2026 as three NLSpecs (spec-only, no code; the README says to feed the spec to a coding agent). Team per Simon Willison: Justin McCarthy (CTO), Jay Taylor, Navan Chauhan; McCarthy personally wrote `jmccarthy/attractor-c`. Sources: [strongdm/attractor](https://github.com/strongdm/attractor), [Willison, "How StrongDM's AI team build serious software…"](https://simonwillison.net/2026/Feb/7/software-factory/), [factory.strongdm.ai/products/attractor](https://factory.strongdm.ai/products/attractor).
- Yegge's relationship is **adjacent inspiration, not authorship**: his Gas Town / software-factory writing anticipated the pattern (HN thread on "Software factories and the agentic moment" mentions him only as "someone whose work apparently inspired this approach"; Dan Shapiro's ["Dark Factories: Rise of the Trycycle"](https://www.danshapiro.com/blog/2026/03/dark-factories-rise-of-the-trycycle/) credits Justin McCarthy with the threshold insight). ## 1. The original `context` object (strongdm/attractor `attractor-spec.md`, §5.1, lines 993–1070)

- **What it is:** "a thread-safe key-value store shared across all stages during a pipeline run. It is the primary mechanism for passing data between nodes." `Map<String, Any>` + RW lock + append-only log; ops are `set/get/get_string/append_log/snapshot/clone/apply_updates`.
- **Who writes it:** two writers. (a) The **engine**, which after every node applies `outcome.context_updates` and sets `outcome`, `preferred_label`, plus built-ins (`graph.goal`, `current_node`, `internal.retry_count.<node_id>`; §5.1 table). (b) **Handlers**, which return `context_updates : Map<String, Any>` in the `Outcome` (§5.2, line 1081) — e.g. codergen writes `last_stage`/`last_response` (§4.5), tool handler writes `tool.output` (§4.10), fan-in writes `parallel.fan_in.best_id/best_outcome` (§4.9). External processes can also feed outcomes via the `status.json` status-file contract (§4.5).
- **Who reads it:** edge `condition` expressions (§10: `key=value`, `key!=value`, `&&`, bare-key truthiness; keys resolve `outcome`, `preferred_label`, `context.*` or unqualified context keys — §10.4); the fan-in handler; the manager-loop's `stop_condition`; and prompts (below). Namespacing is **convention only**: prefixes `context.*`, `graph.*`, `internal.*`, `parallel.*`, `stack.*`, `human.gate.*`, `work.*` (§5.1).
- **Prompt interpolation — nearly none, deliberately:** "The only built-in template variable is `$goal` … Variable expansion is simple string replacement, not a templating engine" (§4.5, line 707). Upstream prompts **cannot** reference context keys. What a node's LLM sees of prior state comes instead from **context fidelity** (§5.4): `full` (reused session/thread), `truncate`, `compact` (default; "structured bullet-point summary: completed stages, outcomes, key context values"), `summary:low|medium|high` — resolved edge attr > node attr > graph default. Thread keys for `full` fidelity resolve node `thread_id` > edge `thread_id` > graph default > subgraph-derived class > previous node ID (§5.4).
- **Lifetime/scoping:** one flat store per run, serialized whole into every checkpoint (§5.3). The **only scoping mechanism is parallel-branch isolation**: "Each parallel branch receives an isolated clone of the parent context" via `context.clone()` (§4.8); branch results come back only as `parallel.results` — branch context deltas are *not* merged (tylergannon `spec.failed.md` line 820 makes this explicit: "individual branch context changes are not merged back into the parent").
- **Loops/cycles:** loops are plain cycles; context is **not** loop-aware. Nothing resets between iterations; a loop iteration sees whatever keys the last pass left (spec's own example: `review -> iterate [condition="context.loop_state!=exhausted"]`, §10.6 line 1763 — the *author* must invent and maintain the loop-state key). Loop bounding is per-node `max_retries` plus the odd `loop_restart` edge attr ("terminates the current run and re-launches with a fresh log directory", §2.7 line 177). The `stack.manager_loop` handler (§4.11) is a supervisor polling loop with `manager.max_cycles`, reading child telemetry out of `stack.*` context keys.

## 2. The routing data plane (§2.7, §3.3, §3.4)

`Outcome` carries `preferred_label`, `suggested_next_ids`, `context_updates`. Edge attrs: `label`, `condition`, `weight`, `fidelity`, `thread_id`, `loop_restart`. Edge selection is a deterministic 5-step cascade (§3.3): (1) condition-matching edges (conditions evaluated **by the engine** against outcome+context); (2) `preferred_label` match against normalized edge labels (strips accelerator prefixes like `[Y] `); (3) `suggested_next_ids`; (4) highest `weight`; (5) lexicographic target-ID tiebreak. **Goal gates** (§3.4): nodes with `goal_gate=true` must have succeeded before the exit node may terminate the run; otherwise the engine jumps to `retry_target` / `fallback_retry_target` (node-level then graph-level), else FAIL.

## 3. Experience reports / critiques

Sparse — the spec is young (Feb 2026) and was shipped without reference code. What exists:

- **Willison's factory writeup** (primary journalism, quoting StrongDM directly): the practices around Attractor ("Code must not be written by humans… not be reviewed by humans", $1,000/day token spend per engineer, holdout scenario tests, Digital Twin Universe clones of Okta/Jira/Slack). Nothing specifically on whether the context KV store worked well.
- **HN thread** ([id=46924426](https://news.ycombinator.com/item?id=46924426)): no experience reports on context/routing mechanisms; code-quality nitpicks on a related repo; jaytaylor (StrongDM) acknowledging early open-sourcing.
- **The most substantive critique in existence is in this lineage itself.** The tylergannon rewrite (rev `0aca8b7`) **already cut the context object** from its normative spec: `docs/spec.md` §5 has typed engine-only state (`completed_nodes`, `node_visits`, `node_attempts`, `last_stage`, `last_response`, `seq`) and §5.5 "Data Between Nodes" declares exactly three surfaces — workspace, session, run directory. §3.3: "Conditions inform the chooser, never the engine … Engine routing logic never reads or compares condition text." §3.4: "`max_visits` is the loop-bounding primitive … The budget is engine bookkeeping only: handlers are not told the visit number. An author who wants the agent to pace itself against the budget says so in the prompt." The earlier attempt that retained upstream Context/Outcome/edge-selection verbatim is preserved as `docs/spec.failed.md` — quarantined by commit `9b63b5e` ("restart spec.md from pristine upstream; quarantine failed attempt"). Outcome-directed routing died with it: Outcome shrank to `next` + `notes`.
- **However, the archived Go implementation still contains the full context data plane**, which the final spec had disowned: `internal/pipeline/conditions/eval.go` (Outcome with `PreferredLabel`, `SuggestedNextIDs`, `ContextUpdates map[string]string`), `internal/pipeline/edgeselect/select.go`, and `internal/pipeline/runner/runner.go` — including two pieces upstream never had: **prompt interpolation of context** (`expandPrompt`, runner.go:1015 — `$attr` metadata expansion plus `{{key}}` context expansion) and **declared context outputs**: `TaskNode.ContextOutputs` lists keys the agent's structured JSON outcome *must* include on success ("The prompt requires these context_updates keys when the node succeeds: …", runner.go:748–752, enforced in `parseStructuredOutcome`, runner.go:791–797). Command nodes take env bindings with `{{context.key}}` interpolation and fail on missing keys (`expandCommandEnvValue`, runner.go:458).
- **Tractor's own written retrospective**: `docs/attractor-archive-inventory.md` rules on each cut. On the routing/context plane: "Rich outcome-directed routing and goal gates — None relative to the chosen model: adding them would let the engine interpret agent verdicts and recreate routing policy outside node occupants. Deliberate exclusion; Tractor is better off without it." But also, notably softer: "Structured command context — Real but narrower gap; worth considering without creating a second workflow data plane," and it calls the richer outcome plane "attractive when a workflow needs structured inter-node data without encoding every decision in a prompt or adding a bespoke node."

# HALF B — Frameworks

## LangGraph
- **Loop:** a cycle via conditional edges (`add_conditional_edges` routing fn returns a node name or `END`) or `Command(goto=...)`; bounded by `recursion_limit` (raises `GraphRecursionError`), with `RemainingSteps` as a declarable state field for graceful degradation.
- **Persistence:** the entire state object — a schema of **channels**, each with a **reducer** (default overwrite; `Annotated[list, operator.add]` appends; `add_messages` upserts by ID). Overwrite channels behave like mutable loop variables; additive channels accumulate across iterations. Checkpointer persists per super-step per thread.
- **Prompt:** user code entirely — a node explicitly builds `model.invoke([SystemMessage(...)] + state["messages"])`; the engine injects nothing (only prebuilt `create_react_agent` prepends a prompt param).
- **Scoping:** the strongest in class — input/output/private schemas, subgraphs with different schemas where parent code marshals in/out (a hand-written stack frame), and the **Send API**: `Send("worker", {"subject": s})` gives each mapped invocation its own payload "not conform[ing] to the graph's overall state schema", with fan-in via reducer merge.
- **Authoring:** code (StateGraph builder → `.compile()`, validation only, no representation change); alternative Functional API where loops are literal `while` loops.
- Sources: docs.langchain.com/oss/python/langgraph/{graph-api,use-subgraphs,quickstart}; reference.langchain.com `Send`, `add_messages`.

## Google ADK
- **Loop:** `LoopAgent` — a workflow agent object that reruns its `sub_agents` list; terminates on `max_iterations` or a sub-agent escalating (`tool_context.actions.escalate = True`, canonical `exit_loop` tool). No per-iteration state: all iterations mutate one shared `session.state` (pattern: critic/refiner overwriting `STATE_CURRENT_DOC` each pass via `output_key`).
- **Prompt:** **explicit declarative templating** — `LlmAgent.instruction` strings interpolate `{var}` from `session.state`, `{artifact.var}`, `{var?}` optional; missing keys error. Instruction-provider functions bypass templating. Data enters state via `output_key` auto-save, `EventActions.state_delta`, or `context.state[...]` in tools.
- **Scoping:** by key prefix only — `app:`, `user:`, `temp:` (invocation-scoped, so spans the *whole* loop run), unprefixed = session. **Nothing like a stack frame**; parallel branches share state, isolated only in conversation-history branch, with collision avoidance by naming convention.
- **Authoring:** Python object composition; ADK 2.0 added a code-defined `Workflow(edges=[...])` graph layer (loops = edges cycling back) but no separate DSL/compile step.
- Sources: adk.dev/agents/workflow-agents/loop-agents/, adk.dev/sessions/state/, adk.dev/agents/llm-agents/, adk.dev/graphs/.

## OpenAI Agents SDK
- **Loop:** only the built-in agent loop inside `Runner.run()` (model → tools/handoff → repeat), capped by `max_turns`. No user-facing loop primitive; iteration = user-written `while` around `Runner.run()`, threading history via `result.to_input_list()`, `session`, or server-side conversation IDs.
- **Prompt:** accumulated message history + `instructions`, where instructions can be a **dynamic function** `(RunContextWrapper, Agent) -> str` — the one hook to render local context into the system prompt. Local context (`Runner.run(context=obj)`) is explicitly "**not** sent to the LLM." Handoffs pass the whole conversation, prunable via `input_filter`.
- **Scoping:** none — one context object type per run. Nearest frame analogue is `agent.as_tool()` (sub-run collapses to a tool result).
- **Authoring:** pure code, no graph, no compile.
- Sources: openai.github.io/openai-agents-python/{running_agents,context,handoffs,agents}.

## Mastra
- **Loop:** first-class builder verbs — `.dountil(step, cond)`, `.dowhile(step, cond)`, `.foreach(step, {concurrency})`. Each iteration's input is the previous iteration's output (schema-typed); the condition receives the step's `ExecuteParams` **plus `iterationCount`** — the engine tells the condition which round it is. `foreach` feeds each array element as that iteration's `inputData` and collects an ordered output array. Cross-step mutable state via `stateSchema`/`setState`.
- **Prompt:** explicit user code — `execute` receives `inputData` (Zod-validated); wiring mismatches handled by `.map()`, `getStepResult(step)`, `getInitData()`; agent-as-step requires mapping to a `{prompt}` field. Nothing auto-injected.
- **Scoping:** the best stack-frame analogue outside LangGraph's Send: a workflow is itself a step; nested workflows have their own input/output schema scope and "each nested workflow execution is independent with its own data flow" (legacy declarative `variables` mapping was replaced by `.map()`).
- **Authoring:** code-first fluent builder that **genuinely compiles to a serializable graph**: builder calls push typed entries (`{type:'loop', loopType:'dountil', serializedCondition,...}`) onto `stepFlow`; `.commit()` builds `stepGraph`/`serializedStepGraph`, which feeds the Studio visualizer; there is also a declarative JSON dynamic-workflow format with `{type:'loop', predicate:{op:'eq',...}}`.
- Sources: mastra.ai/docs/workflows/{control-flow,overview,input-data-mapping}, reference dowhile & dynamic-workflow-definition, `packages/core/src/workflows/workflow.ts`.

## CrewAI
- **Loop:** none in `Crew` (sequential/hierarchical run once; hierarchical adds a manager LLM that delegates dynamically). Loops live in **Flows**: `@router()` returns string labels; a cycle = routing a label back to an earlier `@listen` method; loop bounding is a DIY counter in state (no engine max-turns). State across iterations = Flow state (`self.state` dict or typed Pydantic model), checkpointable via `@persist`.
- **Prompt:** declarative and explicit — `Task.context=[other_tasks]` injects named prior task outputs into the prompt; `{placeholder}` interpolation in `description`/`expected_output` from `kickoff(inputs=...)`; in Flows a listener receives the emitter's return value, everything else via `self.state`.
- **Scoping:** none — one flat state object.
- **Authoring:** code (Flow subclasses; Crew/Task objects), with YAML agent/task config as hydration, not compilation.
- Sources: docs.crewai.com/en/concepts/{flows,tasks,processes}.

# Patterns observed

1. **Loops are either cycles-with-a-counter or an explicit loop node; nobody has both loop-scoped variables and graph authoring.** LangGraph/CrewAI Flows/original Attractor: loop = cycle, state = one shared store, iteration bookkeeping is the author's problem. ADK LoopAgent and Mastra `dountil/foreach` are engine-owned loop primitives — and only **Mastra actually surfaces iteration state from the engine** (`iterationCount` handed to the condition; `foreach` handing each iteration its element as input). Mastra's `foreach` and LangGraph's `Send` are the two real "current chunk is X" mechanisms — per-invocation payloads owned by the engine, results reduced back. Nothing anywhere resembles a scoped **stack of loop frames**; the closest are Mastra nested workflows and LangGraph subgraphs (fresh input/output scope per entry, internals invisible to parent) — both entered once per invocation, not per loop iteration.
2. **Prompt injection splits cleanly:** automatic history accumulation (LangGraph messages, OpenAI SDK, Attractor's `full` fidelity/threads), explicit declarative templating (ADK `{var}`, CrewAI `{placeholder}`/task-context, archived-attractor `{{context.key}}`), or pure user code (LangGraph nodes, Mastra execute). Engine-*synthesized* context summaries (Attractor's `compact`/`summary:*` fidelity) are unique to the Attractor lineage — no mainstream framework generates a prose state briefing for the next node.
3. **Nobody compiles a procedural language to a graph.** The nearest is Mastra: a procedural-*looking* fluent builder with declared schemas and loop verbs that provably compiles to a serialized graph. LangGraph's Functional API goes the other way (procedural instead of graph). A small authoring language with declared loop scopes compiling to a Tractor graph would be genuinely novel territory; Mastra's `serializedStepFlow` is the closest existing proof it's tractable.

**Directly reusable for Tractor:**
- **Mastra's contract shape** is the best fit for "engine-owned iterator": loop primitive owns *(a)* per-iteration input (the chunk), *(b)* an engine-maintained `iterationCount` visible at the decision point, *(c)* prior iteration's output as this iteration's input. All three map onto Tractor without a data plane: (a) = a per-iteration line in the injected prompt preamble, (b) = exposing `node_visits` (Tractor/tylergannon already count it; the archived spec explicitly *chose* not to tell handlers — that's the single doctrine line to revisit: spec.md §3.4 "handlers are not told the visit number"), (c) = Tractor's existing session/workspace channels.
- **LangGraph `Send` / Attractor `work.*` + `context.clone()`** for parallel: per-branch payload injected at spawn, results reduced at fan-in — Tractor's worktree-isolated branches already have the isolation half; the "each branch told its own item" half is the injectable frame.
- **Archived attractor's `context_outputs`** (declared required keys in the structured outcome) is the germ of *typed, declared* loop variables — declaration-first, unlike upstream's free-for-all store — worth stealing if any variable surface returns.
- **ADK's `{var?}` optional-vs-error templating** and prefix-scoping are cautionary: prefix conventions without enforcement is exactly what upstream Attractor had, and it's the weakest part of both.

**Could not find:** any primary Yegge text using "attractor" for DOT pipelines (the premise appears incorrect — origin is StrongDM/Justin McCarthy); any in-the-wild retrospective specifically on whether the shared context KV store worked well or badly (the ecosystem is ~6 months old; implementers' READMEs — jhugman, brynary, samueljklee, microsoft/amplifier-bundle-attractor — report build status, not design experience); and any framework with true per-loop-iteration variable frames.
