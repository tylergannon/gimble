# Research report: iteration, loops, and scoped state in mature workflow systems

Verbatim final report of the deep-research subagent (2026-08-24), commissioned
for the loop-frames design work. See ../memo.md §8.1 for the distillation and
the design deltas taken from it.

---

## Per-system findings

### 1. AWS Step Functions

**Foreach/map:** The `Map` state runs a sub-workflow ("ItemProcessor") per element of a dataset. Two modes: **Inline** (each iteration runs in the parent execution's context, JSON-array input only, ≤40 concurrent, shares the parent's 25k-event history) and **Distributed** (each iteration is a *separate child workflow execution* with its own history, up to 10,000 concurrent, item source can be S3 JSON/CSV/object listings). Item source is declared on the state (`ItemsPath`/`Items`/ItemReader); per-item input is shaped by `ItemSelector`. ([Map state docs](https://docs.aws.amazon.com/step-functions/latest/dg/state-map.html))

**Loop-until:** There is *no loop primitive*. AWS's own tutorial pattern is: a Lambda increments an index-and-`continue` record threaded through state output, plus a `Choice` state with a backward `Next` edge — i.e., a hand-rolled program counter carried in the data plane, with an explicit cycle in the graph. AWS also recommends this pattern to "break up large tasks... or periodically end and restart a long-running execution to avoid exceeding service quotas." ([Iterate-a-loop tutorial](https://docs.aws.amazon.com/step-functions/latest/dg/tutorial-create-iterate-pattern-section.html))

**Scoping (the 2024 Variables feature — the gold mine):** `Assign` declares/sets variables from any of Pass/Task/Map/Parallel/Choice/Wait. The documented rules ([workflow-variables](https://docs.aws.amazon.com/step-functions/latest/dg/workflow-variables.html)):
- "Workflow-local scope": each Map iteration / Parallel branch is its **own scope** that "can refer to outer scope variables" but maintains its own inner variables.
- **No sibling visibility**: branches/iterations "do not have access to variable values from other concurrent branches or iterations."
- **Shadowing is a validation error**: "a variable assigned in an inner scope cannot have the same name as one assigned in an outer scope."
- **Destruction on exit**: "When a Parallel or Map state completes, all of their variables will go out of scope and stop being accessible. Use the Output field to pass data out."
- **Remote scopes see nothing**: "Distributed Map states cannot currently reference variables in outer scopes." (Out-of-process iterations get only their item.)
- All references use values as of **state entry**; all `Assign` expressions evaluate before any assignment lands; limits 256KiB/variable, 10MiB/execution.
- A reserved `$states` variable carries `input`/`result`/`errorOutput`/`context` — the "current frame" is itself modeled as a well-known variable.

**Authoring direction:** Declarative-graph-first (ASL JSON). Code-first layers (CDK, Workflow Studio) *generate* ASL; nothing lifts ASL back to code. Variables were retrofitted precisely because threading data through `ResultPath` output plumbing was miserable — the docs pitch Variables as replacing pass-through chains ("What if those intermediate steps do not need the data?").

### 2. BPMN 2.0 / Camunda

**Foreach:** Multi-instance (MI) activities — a marker on a task/subprocess/call-activity, `isSequential` true/false (sequential MI is literally a foreach). Instance count via `loopCardinality` or a collection: Camunda 7 uses `camunda:collection` + `camunda:elementVariable`; Camunda 8/Zeebe uses `inputCollection` (expression evaluated **when the MI body activates**, must resolve to an array) + `inputElement` (name of the per-instance local variable). ([C7 task markers](https://docs.camunda.org/manual/7.21/reference/bpmn20/tasks/task-markers/), [C8 multi-instance](https://docs.camunda.io/docs/components/modeler/bpmn/multi-instance/))

**Loop-until:** BPMN defines a standard loop marker with a loop condition, but Camunda's engine "does not natively support" it — the documented workaround is to *model the loop explicitly* with gateways and a back edge. MI offers `completionCondition` for early exit (e.g. `nrOfCompletedInstances/nrOfInstances >= 0.6`).

**Scoping:** Variable scopes form a hierarchy (process instance → child executions/subprocesses → tasks). Lookup is child-to-parent: "A variable defined on a parent scope is accessible in every child scope unless a child scope defines a variable of the same name. ... child variables are not accessible from a parent scope" — shadowing is *allowed* in C7 (a classic source of bugs). Each MI instance gets engine-provided locals: `loopCounter` per child; `nrOfInstances`/`nrOfActiveInstances`/`nrOfCompletedInstances` on the MI body. Camunda 8 tightened this: input mappings create *instance-scoped* variables "preventing race conditions in parallel execution," and results leave the instance only via declared `outputElement` → `outputCollection` ("created as a local variable of the multi-instance body"); the docs warn that by default new variables land in process-instance scope visible to all instances — output mappings exist to restrict propagation. ([C7 variables](https://docs.camunda.org/manual/7.21/user-guide/process-engine/variables/))

**Authoring direction:** Declarative-graph-first (BPMN XML, drawn in a modeler). No compile-from-code path in the core product.

### 3. Temporal (and Cadence)

**Foreach:** Just a `for` loop in workflow code, optionally fanning out activities or **child workflows**. Children are the scaling/scoping unit: "each child has its own event history," so a parent can spawn 1,000 children × 1,000 activities where one workflow couldn't; children can run on entirely different workers and "share no local state" with the parent — results return as awaited values. ([Child workflows](https://docs.temporal.io/child-workflows))

**Loop-until:** A `while` loop in code. Long/infinite loops hit the hard event-history limit (51,200 events / 50MB, termination past that; guidance is to stay in the low thousands — [limits](https://docs.temporal.io/workflow-execution/limits)) and the answer is **Continue-As-New**: start a fresh run with fresh history where "the latest relevant state is passed... as arguments to your Workflow" — *only* explicitly passed parameters survive; children don't carry over. This is a manual stack-frame spill at a checkpoint. ([Continue-as-new](https://docs.temporal.io/workflow-execution/continue-as-new)) Continue-As-New and the whole model originate in Uber's Cadence, which Temporal forked.

**Scoping:** Local variables are ordinary language variables, made durable by **replay**: code must be deterministic ("any time your Workflow code is executed it makes the same Workflow API calls in the same sequence, given the same input"); on resume the code re-executes and state is reconstructed by comparing emitted commands to history. Side effects go in activities, "outside the replay path." So scoping is free (the host language's lexical scoping) but paid for with the determinism constraint and history limits. ([Workflow definition](https://docs.temporal.io/workflow-definition))

**Authoring direction:** Code-first, period. There is no graph artifact; the "graph" is implicit in the event history.

### 4. Argo Workflows

**Foreach:** `withItems` (literal list), `withParam` (JSON array from a parameter or *a previous step's output* — "you can generate the JSON in another step"), `withSequence` (numeric range). Each iteration is a separate pod/template invocation receiving `{{item}}` (or `{{item.field}}`); iterations run in parallel by default. Aggregation: "The output of all iterations can be accessed as a JSON array once the loop is done" via `{{steps.X.outputs.result}}`. ([Loops](https://argo-workflows.readthedocs.io/en/latest/walk-through/loops/))

**Loop-until:** **Recursion** — "Templates can recursively invoke each other": the coinflip example has a template conditionally (`when: {{steps.flip-coin.outputs.result}} == tails`) call itself until the condition breaks. Until-loops are literally modeled as recursive template calls, not a loop node. ([Recursion](https://argo-workflows.readthedocs.io/en/latest/walk-through/recursion/))

**Scoping:** No variables at all — only explicit **parameter passing** into templates and declared outputs coming back; each template invocation is a fresh frame whose "scope" is exactly its input parameters. Recursion gives you a call stack for free because each invocation is a new template instantiation.

**Authoring direction:** Declarative-graph-first (YAML). Code-first layers compile *down*: Hera is "the go-to Python SDK... turn Python functions into containerised templates" — Python → Argo YAML, one direction. ([Hera](https://hera.readthedocs.io/en/stable/))

### 5. Airflow

**Foreach:** Dynamic task mapping — `task.partial(y=10).expand(x=[1,2,3])` / `expand_kwargs`. Expansion is deferred to runtime: "the scheduler will create n copies of the task, one for each input," driven by literals or upstream XCom. Each mapped instance is identified by `map_index`. Downstream, results arrive as a "lazy sequence" proxy over the mapped XComs. Limits: `max_map_length` default 1024. ([Dynamic task mapping](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/dynamic-task-mapping.html))

**Loop-until:** **Explicitly unsupported.** The docs state dynamic mapping cannot implement conditional repetition, and Airflow DAGs are acyclic by definition — until-loops get pushed out to sensors/re-triggering/`TriggerDagRunOperator` hacks.

**Scoping:** XComs are a flat global store keyed by `(dag_id, task_id, run_id, key, map_index)` — "identified by a key, as well as the task_id and dag_id it came from." No hierarchy, no lexical scoping, no destruction; "only designed for small amounts of data." ([XComs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/xcoms.html)) Airflow is the cautionary tale: a namespaced global blackboard instead of scopes.

**Authoring direction:** Code-first *authoring* of a declarative *artifact* — Python executes at parse time to produce a static DAG; the code compiles down to the graph, and `expand()` exists precisely because a parse-time Python for-loop couldn't depend on runtime data.

### 6. Inngest (chosen over DBOS)

**Foreach & loop-until:** Ordinary code. `step.run()` checkpoints: "When step.run() finishes successfully, the response is saved in the function run state and the step will not re-run." Loops need no special construct — Inngest "records a counter for each unique step ID... This allows you to run the same step in a loop, without changing the ID." ([Multi-step functions](https://www.inngest.com/docs/guides/multi-step-functions))

**Scoping:** Language-native lexical scope, durable via memoized step results in run state. Determinism is implicit (side effects must live inside `step.run`). Hard limits: **1,000 steps per run**, 4MB per step result, 32MB run state ([usage limits](https://www.inngest.com/docs/usage-limits/inngest)) — same shape as Temporal's history cap: code-first durability meters every iteration.

**Authoring direction:** Code-first only; the "graph" is the memoization log.

## Theory

**Böhm–Jacopini / Dijkstra.** The theorem says sequence + selection + iteration suffice for any computable control flow — but the *proof mechanism* is the instructive part: the folk-theorem construction "replaces the original program's control flow with a single global while loop that simulates a program counter" — i.e., you can always flatten structure into a graph-plus-state-variable, and Kosaraju showed the reverse compression has a strict hierarchy (some flows need depth-n multilevel breaks; below that you *must* add auxiliary boolean variables). Knuth's criticism: the transformation "results in pseudocode" where "the structure of the original program is completely lost." ([Structured program theorem](https://en.wikipedia.org/wiki/Structured_program_theorem)) Note that Step Functions' official loop tutorial — Lambda-maintained `index`/`continue` flags plus a Choice back-edge — *is* the folk-theorem construction performed by hand. A workflow graph with arbitrary cycles and hand-threaded counters is precisely the goto-era artifact Dijkstra's 1968 letter targeted: correctness reasoning requires tracing dynamic histories rather than reading lexical structure.

**Relooper/Stackifier.** Ramsey (ICFP 2022): "in some interesting target languages, including JavaScript and WebAssembly, intraprocedural control flow can be expressed only in structured ways... such structured control flow can be obtained by translating arbitrary control flow" (Peterson–Kasami–Tokura 1973) — but the algorithms are genuinely hard: Emscripten's Relooper (2011) is "heuristic" and "introduces additional code" (label-variable dispatch) when patterns don't match; the principled translation needs dominator trees and two path analyses, and irreducible graphs need node splitting or a dispatch variable. ([Beyond Relooper](https://www.cs.tufts.edu/~nr/pubs/relooper.pdf), [Leaning Technologies on the same problem](https://labs.leaningtech.com/blog/control-flow)) The asymmetry is total: structured → CFG is a trivial syntax-directed lowering; CFG → structured is a research-grade problem that sometimes only succeeds by *adding runtime state*. **Implication for Tractor:** a structured DSL can compile to the existing edge/condition graph losslessly and cheaply; the existing graph cannot be reliably lifted into a DSL, so the DSL must be the source of truth where it's used, and hand-drawn cyclic graphs remain a supported but separate authoring tier.

**van der Aalst's Workflow Patterns.** The MI patterns draw exactly the distinction Tractor needs ([WCP-13](http://www.workflowpatterns.com/patterns/control/multiple_instance/wcp13.php), [WCP-14](http://www.workflowpatterns.com/patterns/control/multiple_instance/wcp14.php), [WCP-15](http://www.workflowpatterns.com/patterns/control/multiple_instance/wcp15.php)):
- **WCP-13** MI with *a priori design-time* knowledge (count fixed in the model);
- **WCP-14** MI with *a priori run-time* knowledge: count "may depend on... runtime factors... but is known before the task instances must be created," instances synchronized at completion — this is "iterate over these N chunks" (chunks discovered at runtime, fixed at loop entry);
- **WCP-15** MI *without* a priori run-time knowledge: "it is possible for additional instances to be initiated" while running, count known only "until the final instance has completed" — the hard pattern most engines fail;
- **[WCP-21](http://www.workflowpatterns.com/patterns/control/new/wcp21.php) Structured Loop**: pre-test (while) / post-test (repeat) with "a single entry and exit point," context condition: only one instance of the loop body active at a time — this is "loop until condition, per-lap sub-goal";
- **[WCP-10](http://www.workflowpatterns.com/patterns/control/structural/wcp10.php) Arbitrary Cycles**: "cycles... with more than one entry or exit point"; the patterns literature notes structured offerings can't represent them and transformation to structured form is only sometimes possible (citing Kiepuszewski et al.) — the workflow-native statement of the Relooper problem. Also **[WCP-22](http://www.workflowpatterns.com/patterns/control/new/wcp22.php) Recursion** (Argo's until-loop mechanism) as an alternative to iteration.

So the taxonomy itself says: *iterate-over-collection* (MI, concurrent instances, synchronizing join, per-instance data) and *iterate-until* (structured loop, one body instance at a time, condition placement pre/post) are different patterns with different context conditions — no mature system unifies them into one construct.

## Synthesis for Tractor

**What the evidence supports: (a) a Map/foreach primitive + (b) SF-style scoped frames now; (c) is a sound but separable later bet.**

**Loop primitive semantics (the convergent design).** Every graph-first system that solved foreach converged on the same five fields, worth copying nearly verbatim from Camunda 8 / Step Functions Map:
1. **Body = a delimited subgraph/sub-workflow**, single entry/exit (WCP-21's context condition), run as a *child scope* — in Tractor's terms, plausibly a fresh agent session and (for parallel) an isolated worktree, mirroring SF Distributed Map's "child execution with its own history."
2. **Item source = an expression evaluated at loop-body activation** (Camunda's `inputCollection`, SF's `ItemsPath`, Argo's `withParam` fed by a previous step). This deliberately targets **WCP-14** (run-time-known count, fixed at entry), not WCP-15. For Tractor, the natural item source is a file the previous node wrote (a chunk list in the run directory) — consistent with the no-data-plane doctrine.
3. **Per-iteration state**: engine injects the current item under a declared name (`inputElement`, `{{item}}`) plus a loop counter (`loopCounter`, `map_index`) into an iteration-local frame; iterations never see sibling state.
4. **Exit semantics**: iteration state is destroyed; only a **declared aggregation** survives (`outputElement`→`outputCollection`, SF `Output`, Argo's results-as-JSON-array). Tractor's analog: each iteration's declared artifact path(s), collected by the engine.
5. **Early exit** via `completionCondition` — and note sequential MI + completion condition is *already* most of "loop until condition with per-lap sub-goal."

**Until-loops**: keep them as graph cycles (Tractor already has this; it's Argo recursion / SF Choice-loop / Camunda's documented workaround), but consider blessing a structured form (a cycle annotated as a WCP-21 loop with a pre/post-test prose condition) so the engine knows where the body starts/ends — which is exactly what makes frames attachable.

**Scoping rules worth copying (SF Variables, 2024):** outer-readable, sibling-invisible, **shadowing forbidden** (validation-time error — cheap and kills the whole Camunda-7 shadowing bug class), **destroyed at scope exit** with explicit export only, and **remote/parallel iterations see only their item** (the Distributed Map rule — which for Tractor is also the honest rule, since a fresh agent session physically can't see the parent's context anyway). For prompt injection, SF's reserved `$states` object is the model: the "frame" is a well-known structured value the engine composes into each state — for Tractor, a small YAML/text block (current item, lap number, lap goal, exports from prior laps) prepended to the node's prompt.

**Compile direction:** unanimous. Code-first systems (Temporal, Inngest, Airflow-the-Python-layer, Hera, CDK) all *lower* code to a graph/log artifact; no system lifts graphs to code, and PL theory (Relooper, Kosaraju, WCP-10) says lifting is impossible in general without adding state variables or duplicating nodes. So if Tractor builds (c), the DSL compiles to the existing graph format one-way; hand-authored graphs and compiled graphs coexist; never attempt round-tripping. Also note the code-first tax Tractor would *not* pay by staying graph-first: Temporal/Inngest buy lexical scoping with determinism constraints and hard iteration budgets (51,200 events; 1,000 steps) plus an escape hatch (continue-as-new) that is itself manual state-threading.

**Single most instructive precedent:** **AWS Step Functions' 2024 Variables + JSONata release.** It is the one case of a mature, deliberately data-plane-minimal declarative graph language retrofitting exactly what Tractor is considering — scoped variables layered onto an existing graph — and it published crisp scoping rules (workflow-local frames on Map/Parallel, outer-read/no-sibling/no-shadow, destroy-on-exit, explicit Output export, remote scopes blind), explicitly motivated by the pathology Tractor would otherwise inherit: users hand-threading counters and pass-through payloads (their own loop tutorial) — the Böhm–Jacopini folk construction done manually. Runner-up: Camunda 8's multi-instance attribute set as the cleanest loop-primitive field vocabulary.

**Couldn't determine:** Camunda 7 docs never explicitly state what happens to scope-local variables at scope completion (behavior — destruction with the execution — is implied, not documented); Inngest's docs don't state a formal determinism contract (step identity = ID + invocation counter, so reordering loops across a deploy can misalign memoization — implied, not spelled out); Argo docs give no recursion depth limit; whether SF's "Distributed Map cannot reference outer variables" restriction has since been lifted ("currently" in the docs as fetched); the workflowpatterns.com pages state context conditions but not normative "structured is better" arguments — that argument lives in the Kiepuszewski/Kiel citations on WCP-10, which were not retrieved.
