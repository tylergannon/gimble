# Temporal Go: replayed command history

**Purpose.** Temporal Go is the strongest inspected example of code-authored orchestration that preserves an execution across worker loss by replaying recorded history. It is useful here mainly as a measure of the constraints and carrying costs that accompany exact resume, not as evidence that Tractor needs them.

**Findings.**

- A workflow can express conditional routing in ordinary-looking Go: the official sample reads an activity result, uses a `switch`, and schedules exactly one matching activity (`durable/temporal-go/choice-exclusive-workflow.go.txt:24-46`; [pinned sample](https://github.com/temporalio/samples-go/blob/a3d54e384db1842459c57df7d9d3db66b204d9db/choice-exclusive/workflow.go#L24-L46)). Thus an ordinary `for`/`if`-shaped authoring surface can describe a goal-seeking loop; it does **not** yield a complete pre-run DAG when the next branch depends on a future activity or agent result.
- The workflow body does not directly perform the effect: `ExecuteActivity` only requests/schedules an activity and immediately returns a `Future` (`durable/temporal-go/workflow.go.txt:211-263`; [pinned source](https://github.com/temporalio/sdk-go/blob/9aae5eec926f359f1fb986b7d3125bd968d1067a/workflow/workflow.go#L211-L263)). The public Go guide additionally states that workflow code must be deterministic and routes external I/O through Activities; treat that as vendor documentation, not an observed run ([guide](https://docs.temporal.io/develop/go/workflows)).
- For short nondeterminism, `SideEffect` records the returned value and returns that stored value on replay; the source explicitly warns that closure mutation is not replay-safe (`durable/temporal-go/workflow.go.txt:416-456`; [pinned source](https://github.com/temporalio/sdk-go/blob/9aae5eec926f359f1fb986b7d3125bd968d1067a/workflow/workflow.go#L416-L456)). This is memoization of a decision/value, not a general external-effect transaction.
- Code evolution is part of the mechanism: the SDK says incompatible changes while workflows run break determinism, then provides version markers that replay the recorded version (`durable/temporal-go/workflow.go.txt:526-536`; [pinned source](https://github.com/temporalio/sdk-go/blob/9aae5eec926f359f1fb986b7d3125bd968d1067a/workflow/workflow.go#L526-L536)). That maintenance cost has little payoff if a resumed Tractor run is deliberately allowed to revalidate the repository and replan.
- Local activities illustrate the durable boundary: their result is serialized into history so a different worker can replay without running the local activity again (`durable/temporal-go/workflow.go.txt:265-309`; [pinned source](https://github.com/temporalio/sdk-go/blob/9aae5eec926f359f1fb986b7d3125bd968d1067a/workflow/workflow.go#L265-L309)). It does not establish exactly-once completion of an arbitrary HTTP call made inside an Activity; activity idempotency/compensation remains application work.

**Recovery and ambiguity.** Event history makes the scheduler's recorded command decisions reproducible and can avoid repeating a recorded side-effect result. There remains an effect boundary: if an Activity causes an external PR/deploy and the worker dies before Temporal knows its completion, retry may repeat it. The copied SDK does not make a stronger end-to-end claim, so give the effect an idempotency key or make the remote target queryable. For a coding loop that can inspect Git, CI, and deployment state after restart, this is exactly the cost that can be avoided by not adopting replay.

**Visualization.** The supplied artifacts show runtime-visible command/activity boundaries, and the side-effect options note a summary is shown in UI/CLI (`durable/temporal-go/workflow.go.txt:459-465`). They do not expose a source-level static graph compiler. A source-derived outline could still show syntactic activity calls and both branches, with dynamic calls marked opaque; it cannot honestly promise the concrete route that a future activity or agent result selects. A separate declared graph is optional product metadata, not a conclusion forced by this source.

**Themes.** deterministic replay; recorded decisions; effect isolation; dynamic routing; runtime trace rather than static plan.

**Gotchas.** Do not infer that `workflow.Go`, standard goroutines, map iteration, wall clock, or arbitrary I/O are interchangeable. The official guide restricts workflow logic; the copied SDK only proves the dedicated APIs, so an implementation assessment needs a runnable spike before relying on a particular construct. Do not confuse `SideEffect` result replay with atomic execution of a remote irreversible operation.

**Retrieval recipe.** For exact-resume constraints, start at `durable/temporal-go/workflow.go.txt:416`; for code-versioning costs, `:526`; for dynamic routing that defeats pre-run expansion, `durable/temporal-go/choice-exclusive-workflow.go.txt:24`.

**Status and license.** API evidence on 2026-09-08: active/non-archived, `main` `9aae5eec926f359f1fb986b7d3125bd968d1067a`, commit date 2026-09-08, latest release `v1.48.0` (2026-08-18), MIT; see `durable/status.json` and `durable/MANIFEST.md`.

**Unknowns and counterevidence.** No Temporal server was started and no replay or UI was observed. The source is evidence of SDK API semantics, while any server persistence/visibility claim needs server/docs evidence. Temporal can be the appropriate trade for business processes that require exact continuation across long sleeps/signals; that is not established for a coding workflow whose accepted recovery contract is fresh validation against repository state.
